# blueprint-agent ↔ starter-foundry integration audit (post-v0.11.0)

Cross-portfolio audit verifying that blueprint-agent's consumption of `@tangle-network/starter-foundry` survives the v0.11.0 architectural changes (PRs #100, #105, #106, #107).

## TL;DR

- **blueprint-agent consumes only public-API exports** of starter-foundry — no bundle-content reads, no registry-shape coupling, no references to the deleted `agent-platform-ts` / `agent-orchestrator-service-ts` families.
- **No breaking changes for v0.11.0.** Every symbol blueprint-agent imports is still exported from the same path. The CLI subprocess contract (`compose-prompt --prompt … --out …`) is unchanged. Bundle filename renames (`system-prompt.md` → `AGENTS.md`, `agent-roster.json` → `agents.json`) do not surface to blueprint-agent because it never reads bundle output by filename.
- **Recommended action:** safe to bump the vendored `apps/web/vendor/tangle-network-starter-foundry-0.8.0.tgz` pin to v0.11.0 once published. One latent fragility (a deep import of `ENSURE_DEV_SERVER_INSTRUCTION` via `dist/lib/agent-context.js`) should be tracked but does not block the bump — the symbol still exists in v0.11.0 at the same path.

Not performed (would mutate blueprint-agent):

- Live `pnpm install` against v0.11.0 from GitHub Packages. The vendored-tarball pin in `pnpm.overrides` would have to be edited to a registry spec, and that's an act blueprint-agent should sequence with its own CI rather than from a starter-foundry worktree audit.

## Recommendation

1. **Bump is safe.** Once starter-foundry v0.11.0 publishes to GH Packages, blueprint-agent can swap the vendored tarball for a registry pin without source changes. No call sites need modification.
2. **Keep the vendored tarball workflow** until GH Packages auth is solved cleanly inside the dev container — `pnpm.overrides` with a literal tarball URL is the only spec form that bypasses `.npmrc` scope routing (per blueprint-agent's `.evolve/reflections/2026-04-09-session-reflect.md:75` and `docs/agentic-bench/SPEC.md:285-325`).
3. **Coordinate one follow-up in starter-foundry** (separate PR; not a blocker for v0.11.0): export `ENSURE_DEV_SERVER_INSTRUCTION` from the `./agent-context` subpath barrel so blueprint-agent's deep import (`scripts/experiments/lib/blueprint-agent-prompt.ts:40-44`) can move to the public path. Without this, the deep import remains technically internal and could break silently on a future internal restructure of `agent-context.ts`.
4. **No flagging needed for the deleted families.** blueprint-agent never wrote a code path that depended on `agent-platform-ts` or `agent-orchestrator-service-ts`. The closest match (`langgraph-agent-platform-ts`) is a distinct family and remains in v0.11.0.
5. **No flagging needed for the AGENTS.md / agents.json renames.** blueprint-agent's role is to invoke the CLI and let it write whatever the bundle says. The agent-context wording (already shipped in 0.8.0) tells the agent to read `AGENTS.md` — the rename is internally consistent across both starter-foundry versions blueprint-agent has consumed.
