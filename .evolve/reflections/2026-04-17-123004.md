## Skill Effectiveness

### Meta-harness — what worked

1. **Worktree isolation for parallel proposers** — let me dispatch A/B/C concurrently, zero file contention. Necessary primitive.
2. **Per-scenario eval output** — without this, the ideasai capHit=0.18 diagnosis would have been invisible. Aggregate metrics only would have said "eval is mostly green."
3. **Lineage merge = composition when files are orthogonal** — A/B/C touching different files made generation 1 a merge, not a tournament. This wasn't luck; I designed it that way. But the skill doesn't codify it.

### Meta-harness — what didn't

1. **No proxy-metric check at bootstrap.** Step 0 of the skill says pick dimensions. It doesn't say: *justify why moving each dimension will move a product metric.* Operator caught this; skill should.
2. **Variant archive duplicates git history.** `.evolve/meta-harness/variants/fast_keywords.ts` is now identical to `src/lib/keywords.ts @ 58f092a`. The skill mandates the archive. After merge, the source file should be replaced by `{commit, path, lineCount}` — keep only the `.meta.json`.
3. **Baseline noise window unspecified.** First baseline was p95=0.855; clean re-run said 0.902. ~5% drift. Skill should require ≥3-run median baseline before calling a variant a winner. I did that for the merged variant (5 runs) but not for the proposer baselines.
4. **Worktree state leak.** Proposer C's worktree didn't have `scripts/meta-harness-eval.mjs` (I created it in main after the proposer was dispatched). Proposer had to copy it in. The skill's worktree bootstrap should snapshot `.evolve/` + `scripts/` at dispatch time.
5. **No "failure" iteration logged.** evolution.jsonl only has successes. The paper's worked example says the skill learns from failures. A zero-failure generation gives no dead-end pivots to study.

### Skill effectiveness elsewhere (from INDEX.md)

- `/pursue` ships but misses pre-merge security checks (2 independent signals from agent-dev-container + blueprint-agent). Unrelated to this session but worth noting for cross-project action.
- `/evolve`-style workflows have the highest success density when the metric is already well-defined. This session adds confirming evidence: when the metric wasn't connected to product, the skill still "succeeded" by its own measure but the operator had to flag it.

## Product Signals

1. **The proxy-metric gap is universal.** Any agent-driven eval system has it. A skill called `/validate-metric` that takes a target dimension and asks "what product outcome moves when this moves?" — and refuses to proceed if you can't answer — would be load-bearing across evolve/pursue/meta-harness/harden. Who would pay: anyone running offline evals on LLM systems and wondering why the production number doesn't match.
2. **Scaffold-value question for blueprint-agent** is itself a productizable answer. If we can demonstrate "scaffolded starts ship in N fewer turns" on real agentic runs, that's a landing-page stat AND a reason for customers to prefer blueprint-agent over a blank-slate agent UI.
