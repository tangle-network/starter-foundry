# Measurement freshness contract

This doc explains how `starter-foundry`'s scorecard stays honest, and what you need to do — or not do — to keep it that way.

## One-line version

> `.evolve/scorecard.json` self-heals. If it's stale when you read it, it regenerates itself on the next read. You do not need to run pipelines manually.

## Data flow

```
.evolve/traces/buildouts.jsonl          ← source of truth (mined from
                        │                   local Claude Code session transcripts,
                        │                   gitignored due to size)
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
  analyze-buildouts  infer-capability  replay-traces
          │             -gaps                │
          ▼             ▼                    ▼
  buildout-analysis  capability-gaps    buildout-analysis
      .json              .json          -internal.json
    (historical)      (historical)      (counterfactual:
      tracked           tracked         against current
                                        registry)
          │             │                    │
          └─────────────┼────────────────────┘
                        ▼
                  refresh-scorecard
                        │
                        ▼
                 .evolve/scorecard.json  ← what governor/CI/humans read
                    (tracked)
```

## Freshness rules

A derived file is **fresh** when its mtime ≥ the mtime of `.evolve/traces/buildouts.jsonl`. Otherwise it's **stale**.

| File | Fresh? | Stale behavior |
|---|---|---|
| `buildout-analysis.json` | mtime ≥ source mtime | auto-regenerated by `refresh-scorecard.mjs` self-heal (~1s) |
| `capability-gaps.json` | mtime ≥ source mtime | auto-regenerated by `refresh-scorecard.mjs` self-heal (~1s) |
| `buildout-analysis-internal.json` | mtime ≥ source mtime | auto-regenerated by `refresh-scorecard.mjs` self-heal (~0.5s) |
| `scaffold-quality-audit.json` | mtime ≥ source mtime | **flag-only** — regen is 20–30 min; operator runs `node scripts/audit-scaffold-quality.mjs --smoke-compose` when intentional |
| `scorecard.json` | mtime ≥ all-of-above | regenerated when `refresh-scorecard.mjs` runs (explicit or self-heal trigger) |

## How to stay honest

### You probably don't need to do anything

The scorecard self-heals. Reading it automatically regenerates stale inputs first.

### When you might want to do something

**After pulling a new `buildouts.jsonl` from a VB sweep:**
```bash
pnpm measure:refresh
```
Runs every stale stage. <5s total when nothing's changed, <10s when everything's stale.

**Before pushing a branch:**
Nothing — the `pre-push` hook runs `measure:refresh --dry-run` and blocks if drift exists. Run `pnpm measure:refresh && git add .evolve/ && git commit` to unblock.

**To install the pre-push hook on a fresh clone:**
```bash
pnpm setup:hooks
```
Idempotent.

**To check freshness without regenerating:**
```bash
pnpm measure:check
```
Exits 0 if clean, 2 if drift.

## How the scorecard decides what's real

When `refresh-scorecard.mjs` runs, it:

1. Checks mtime of every analysis file vs source.
2. **Self-heal:** for each stale analysis that has a fast regen path (<5s), spawns the regenerator before reading. This runs `analyze-buildouts.mjs`, `infer-capability-gaps.mjs`, and `replay-traces.mjs` as needed.
3. Reads the freshly-regenerated (or already-fresh) files.
4. **Counterfactual fallback:** if `buildout-analysis.json` is STILL stale after self-heal (regen failed) and `buildout-analysis-internal.json` is fresh, reads the internal one instead. Marks the affected flows with `source: 'counterfactual'` in the output so consumers know.
5. Emits the scorecard with per-flow staleness flags and a `buildoutSource` field (`historical` or `counterfactual`).

### What counterfactual means

- **Historical** (`buildout-analysis.json`): "what actually happened on the last VB sweep" — the real pass rates, real failing scenarios, real turn counts.
- **Counterfactual** (`buildout-analysis-internal.json`): "what would happen if the captured prompts were re-run today, given the current registry" — always fresh because it replays against live code, but it's a projection, not a measurement.

Both are useful. The scorecard prefers historical when fresh and falls back to counterfactual only when historical is stale AND internal is fresh — never silently loses the distinction.

## When to disable the self-heal

In **tests** — set `STARTER_FOUNDRY_NO_SELF_HEAL=1` to prevent recursion through fixture paths.

In **a run of a subset of stages** — `scripts/measure-refresh.ts` sets this and propagates it to sub-invocations of `scripts/refresh-scorecard.ts`. Run it by hand with `pnpm measure:refresh`; there is no scheduled workflow that runs it.

In **manual debugging** — when you want to see the stale data without the scorecard covering for it: `STARTER_FOUNDRY_NO_SELF_HEAL=1 node scripts/refresh-scorecard.mjs`.

## Pre-push hook — bypass and management

The hook is installed at `.git/hooks/pre-push` by `pnpm setup:hooks`. Bypass options:

- **Per-push** (for hotfixes that don't touch measurement state):
  ```bash
  git push --no-verify
  ```
- **Per-clone** (for environments where the pipeline can't run):
  ```bash
  git config hook.skip-measure-check true
  ```
- **Uninstall** (not recommended):
  ```bash
  rm .git/hooks/pre-push
  ```

## Why this design

Gen-2 shipped a staleness *gate* — the scorecard flagged which flows were reading stale data. That detected the problem but didn't fix it; the fix still required an operator to remember to run `analyze-buildouts.mjs`.

Gen-3 closes the loop. Self-heal makes stale reads impossible (on the fast-regen path), the pre-push hook makes stale commits impossible, and the counterfactual fallback gives a fresh-by-construction substitute for the one slow-regen case (`scaffold-quality-audit.json` isn't self-healed because 20-minute spawn inside a read is unacceptable — operator still runs that explicitly when auditing).

The thesis: **measurement freshness should be a property of the system, not a responsibility of the operator**.
