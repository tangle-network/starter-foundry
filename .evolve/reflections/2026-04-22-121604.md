## Session flow analysis

### Flow 1: "push it, take the lead" → autonomous multi-step execution
**Frequency:** 5× this session.
**Pattern:** user hits authorization ("green light", "push it", "take lead") → I execute 10-30 min of code + ops + push/publish → report concrete next.
**Outcome:** consistently successful when scope was clear (tcloud publish, port change, deep-clean). Less successful when scope was wider than I scoped (the sandbox backend ended up hitting billing architecture late).
**Automation potential:** NONE. This IS the pattern. But a pre-execution scope-confirmation + mid-execution pivots-log would reduce the "went farther than user expected" risk.

### Flow 2: Operator surfaces architectural gap mid-execution → course-correct → ship better
**Frequency:** 4× (BYOB billing, LiteLLM, user-key forwarding, sandbox-api-owns-meter).
**Pattern:** I'm mid-implementation → user asks a sharp architectural question → I audit → find real flaw → fix before shipping.
**Outcome:** saved shipping flawed architecture 4 times this session. Highest-leverage pattern.
**Automation potential:** MEDIUM. A pre-PR "architecture audit" pass against a set of known invariants (user-identity propagation, double-billing, cross-service trust) could catch most of these autonomously. Worth building as a `/critical-audit` preset for cross-service work.

### Flow 3: Squash merge → forward-port friction → extra PR
**Frequency:** 2× (starter-foundry #37→#39, cli-bridge PR #1 review-fixes → PR #4).
**Trigger:** squash-merging a base branch while a stacked PR still has commits on it.
**Automation potential:** HIGH. A pre-merge check: "is this PR's HEAD branch base to any other open PR?" — if yes, warn + suggest `gh pr edit --base main` on the dependent PRs first. ~40 LoC.

### Flow 4: Test with stored keys → expired/wrong-scope → operator pastes fresh
**Frequency:** 3× in this session alone (`TANGLE_ROUTER_USER_KEY` expired, user-provided key wrong scope, sandbox-api key detour).
**Automation potential:** HIGH. `scripts/verify-key-scope.mjs` — probes a given `sk-tan-*` against router + sandbox-api + `id.tangle.tools` and surfaces scope mismatches in one roundtrip. Saves the "403 → log inspection → retry" loop every time.

### Flow 5: Prod deploy by rsync + docker build + compose recreate
**Frequency:** 3× (cli-bridge initial, cli-bridge after rename fixes, router after user-auth forwarding).
**Automation potential:** HIGH. `scripts/deploy-cli-bridge.sh` + `scripts/deploy-router.sh` — ~60 LoC each. Manual ops today; scripted is inevitable as Tangle ships more services.

## Operator questions that revealed gaps

## Product signals (commercial)

1. **`tcloud.bridge({harness:'sandbox', model:'<profile-id>'})` as agent-marketplace primitive.** Agents become OpenAI-addressable model ids. A third party could publish an AgentProfile with a monetization wrapper; buyers dispatch via standard chat-completions API; Tangle routes + takes a share. Foundation is in place; needs a catalog + payment wrapper.

2. **Unified billing ledger view.** There's no cross-service view of user U's deducts — today it's "check router logs + check sandbox-api logs + join by userId." A platform dashboard at `id.tangle.tools/billing/ledger` would be table stakes.

3. **Key-scope creation UX.** `tcloud keys create` doesn't expose scope. Users will hit "works on router, 401s on sandbox" forever until scope is either default-all-products or visible at create time.

4. **Cross-service identity propagation (`X-Tangle-Forwarded-Authorization`).** The pattern I invented for cli-bridge → sandbox-api should be a platform contract. Document it. Verify it. Every new service should do it the same way.

5. **Deploy automation for Tangle services.** Manual rsync + docker build + compose recreate is sustainable at 2-3 services; not at 10. The ops toil has non-linear growth.

## Patterns worth carrying forward

- **Audit identity propagation before shipping cross-service code.** The user-key-forwarding audit this session caught a real money flaw before it shipped. Bake this into a checklist.
- **Forward the key > forward a signed userId.** Uses existing `verifyKey` paths; no new trust mechanism. Simpler is better when platforms already solve auth.
- **Operator's "why wasn't X migrated EXACTLY" is the sharpest signal.** Always re-audit rather than defend initial design. Cost 2 min to check; saved shipping wrong code.
- **Cli-bridge-like harness + AgentProfile + OpenAI-compat API = agent-marketplace foundation.** Filed under product signals; worth a strategy session.
